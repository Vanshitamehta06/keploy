## The Core Problem with Testing Go Services <span id="the-problem" />

Writing integration tests for Go APIs that talk to MongoDB usually leads to two bad options:

1. **Interface & mock boilerplate**: You wrap every database call in interfaces, use `gomock` or `testify`, and spend hours handwriting mock structs. When the real MongoDB driver behavior changes, your mocks drift and tests give false confidence.
2. **Heavy test databases**: You spin up real MongoDB containers via Testcontainers. It works, but it slows down CI and requires database cleanup scripts.

Keploy takes a different approach: **it captures real HTTP and database network traffic at the socket level using eBPF/proxying**, writes them as readable YAML files, and replays them later as self-contained tests.

---

## How It Works <span id="how-it-works" />

You run your application normally. Keploy hooks into the network layer without requiring SDK wrappers or code edits:

<ArchitectureFlow />

- **In Record Mode**: You make regular HTTP requests. Keploy saves the incoming request/response pair into `tests/test-1.yaml` and the outgoing MongoDB BSON wire packets into `mocks/mock-1.yaml`.
- **In Test Mode**: Keploy restarts your Go app, replays the recorded HTTP call, and **serves the recorded MongoDB response from the mock file**. MongoDB does not even need to be running.

## Prerequisites <span id="prerequisites" />

You need **Go 1.20+**, **Docker & Docker Compose**, and the **Keploy CLI**.

Install the Keploy CLI:

```bash
curl --silent -O -L https://keploy.io/install.sh && source install.sh
```

Clone Keploy's official Gin + MongoDB URL shortener sample:

```bash
git clone https://github.com/keploy/samples-go.git
cd samples-go/gin-mongo
```

The sample has two simple endpoints in `main.go`:
- `POST /url`: Accepts a URL, generates a short code, saves it to MongoDB collection `urls`.
- `GET /:param`: Looks up the short code in MongoDB and redirects (HTTP 301).

## Step 1: Record Real Traffic <span id="step-1-record" />

Start your application wrapped inside `keploy record`:

```bash
keploy record -c "docker compose up" --container-name "ginMongoApp" --build-delay 15
```

<Callout type="gotcha" title="Why --build-delay is needed">
  When using Docker Compose, the Go container and MongoDB container take a few seconds to compile and bind ports. Without <code>--build-delay 15</code>, Keploy might attempt to hook into the container before it is ready.
</Callout>

Once Keploy outputs that it is ready to record, open a separate terminal and send an API call:

```bash
curl --request POST \
  --url http://localhost:8080/url \
  --header 'content-type: application/json' \
  --data '{"url": "https://keploy.io"}'
```

Response:

```json
{"url": "http://localhost:8080/L9x2q"}
```

Now test the redirect endpoint using the generated short code:

```bash
curl -i http://localhost:8080/L9x2q
```

Press `Ctrl + C` in the Keploy terminal to stop recording. Keploy flushes the recorded files to your workspace.

<Callout type="gotcha" title="Graceful shutdown matters">
  Make sure your Go app handles <code>SIGINT</code> / <code>SIGTERM</code>. If an app is forcefully killed (<code>kill -9</code>), Keploy may terminate before writing buffered mock files to disk.
</Callout>

## Step 2: What Keploy Created <span id="step-2-artifacts" />

Check your project directory. Keploy generated a new `keploy/` folder containing two files:

```text
keploy/
└── test-set-0/
    ├── mocks/
    │   └── mock-1.yaml   # Low-level MongoDB wire mocks
    └── tests/
        └── test-1.yaml   # Recorded HTTP request and response
```

Toggle between the two files below to see how they look:

<YamlViewer />

Notice two important details:
1. **`assertions.noise`**: Keploy automatically flags volatile headers like `header.Date` as noise so tests don't fail due to timestamp differences.
2. **`kind: Mongo`**: The mock isn't a high-level function mock—it is the raw MongoDB BSON wire protocol packet. This guarantees your mocks represent real driver behavior.

## Step 3: Run the Tests Without MongoDB <span id="step-3-test" />

This is the most useful part: **you can test the application with MongoDB completely turned off.**

Stop your local MongoDB or let Keploy run in test mode:

```bash
keploy test -c "docker compose up" --container-name "ginMongoApp" --delay 10
```

Keploy starts the app, injects the recorded HTTP request, intercepts the Go app's database call, and serves the response from `mock-1.yaml`.

Terminal output:

```text
🐰 [Keploy] Starting test execution for test-set-0
⚡ Running test-1: POST /url
↳ Intercepted outbound Mongo call -> Served from mock-1.yaml
```

## What Happens When Code Breaks? <span id="step-4-regression" />

If someone changes the response format or status code in `main.go`:

```diff
- c.JSON(http.StatusOK, gin.H{"url": "http://localhost:8080/" + shortCode})
+ c.JSON(http.StatusCreated, gin.H{"short_url": "http://localhost:8080/" + shortCode})
```

Running `keploy test` immediately catches the regression with a visual diff:

```text
❌ test-1 FAILED
- Status Code: Expected 200 OK, got 201 Created
- Body Diff:
  - {"url": "http://localhost:8080/L9x2q"}
  + {"short_url": "http://localhost:8080/L9x2q"}
```

## Key Takeaways from Running the Quickstart <span id="takeaways" />

- **Zero code changes**: You don't wrap routers or inject test interfaces into production Go code.
- **No database dependency during testing**: You can run integration test suites in CI pipelines without provisioning MongoDB instances.
- **Wire-level accuracy**: Because mocks are captured from real TCP socket packets, they don't suffer from manual mock drift.
